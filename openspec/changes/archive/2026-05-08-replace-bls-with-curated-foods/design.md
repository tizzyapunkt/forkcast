## Context

forkcast currently sources its German nutrition data from a build-time-generated artifact (`backend/data/bls.json`) derived from the BLS 4.0 (2025) CSV. The BLS source is wired through three layers: a domain scorer (`score-bls-match.ts`) with a 5-tier matching algorithm (exact / whole-word / prefix / token-start / substring), an in-memory adapter (`InMemoryBlsService`) that loads the JSON and indexes folded names, and a `CompositeIngredientSearchService` that fans out to BLS and Open Food Facts in parallel. The same port (`IngredientSearchService`) feeds the manual log drawer, the recipe ingredient picker, and the AI recipe importer's per-ingredient matcher.

The BLS dataset has three concrete pain points:
1. **Names are not user-friendly.** Entries like `Käse, Camembert, 30 % Fett i. Tr.` are useful for a nutritionist but noisy in the search results we present to a single home cook. Canonical names are inconsistent across categories.
2. **There are no synonyms.** Querying `Tomate` does not find `Tomaten, Cherry`; querying `chicken breast` works only because BLS happens to ship an English column. The AI recipe importer compensates with raw fuzzy matching, which is brittle when the recipe wording is colloquial (`Möhre` vs `Karotte`, `Lachs` vs `Lachsfilet`).
3. **No piece weights.** Pieces are estimated entirely by the vision model on every recipe import; we have no on-disk reference values to anchor those estimates or to render in the manual UI ("1 mittlere Zwiebel ≈ 110 g").

This change replaces BLS with a small, hand-curatable, AI-seeded JSON of raw whole foods we actually cook with. The architectural shape (port, composite, scorer, adapter) stays; the *data* and the *names of the symbols* change. A separate but related UX flip moves OFF to the default in the manual search drawer, leaving FOODS as an opt-in.

## Goals / Non-Goals

**Goals:**
- Replace the BLS source end-to-end with a curated FOODS source that exposes the same `IngredientSearchService` contract.
- Each FOODS entry carries a canonical German name, a synonyms list, per-100g macros, a reference unit (`g` or `ml`), and an optional list of named piece weights.
- Synonyms participate in name-match scoring at the same tier-quality the canonical name does, so colloquial queries (`Karotte` for `Möhre`) match cleanly.
- The seed dataset (~100–150 entries) is generated by a committed build script that calls Claude through the existing Anthropic SDK with a curated input list of food keys. Output is deterministic enough for diff review and is committed to the repo.
- Flip the manual search drawer's default source from local-catalog to OFF, with FOODS as an opt-in toggle. The AI recipe importer continues to match against FOODS only.
- All BLS code, data, and CSV are removed.

**Non-Goals:**
- No micronutrients (fiber, sodium, vitamins). Macros only — same shape as today.
- No fuzzy/typo-tolerant matching beyond the existing folded-substring tiers. Synonyms cover the realistic miss-cases.
- No DB engine. JSON file persistence stays consistent with the rest of the project (recipes, log entries, nutrition goal).
- No live AI generation at runtime. The AI is used only at build time; the running backend has no AI dependency for FOODS search.
- No multi-language UI (canonical name stays German; synonyms can mix DE/EN to aid the importer).
- No bulk admin UI for editing entries. The JSON is reviewed in PR diffs and edited by hand or by re-running the build script.
- No piece-weight inference *back* into the AI recipe importer's prompt. The vision model continues to estimate per-call (per the existing `ai-recipe-import` spec); the curated piece weights are stored on the entry for future UI surfacing and as a reference, but the importer's prompt contract is not changed in this iteration.

## Decisions

### 1. Data model: canonical name + synonyms + piece-weight list

```ts
interface FoodEntry {
  id: string;                  // stable kebab-case key, e.g. "moehre"
  name: string;                // canonical German display name, e.g. "Möhre"
  synonyms: string[];          // DE+EN aliases, e.g. ["Karotte", "carrot", "Mohrrübe"]
  unit: 'g' | 'ml';            // reference unit
  macrosPer100: {
    calories: number;
    protein: number;
    carbs: number;
    fat: number;
  };
  pieces?: PieceWeight[];      // optional; absent for things never piece-counted (oils, milk)
}

interface PieceWeight {
  label: string;               // German label, e.g. "klein" | "mittel" | "groß" | "Filet"
  grams: number;               // typical mass in grams
}
```

The indexed runtime form (`FoodIndexedEntry`) folds `name` and each synonym into an array of folded strings (case- and diacritic-stripped) for scoring, mirroring how BLS was indexed.

**Rejected:** a single `aliases` field that includes the canonical form. Keeping `name` separate makes the canonical/synonym distinction unambiguous in mappers and in search-tie-breaking logic, and keeps result rendering trivial (`name` is what we show).

**Rejected:** language-tagged synonyms (`{ de: [...], en: [...] }`). The scorer doesn't need to know the language; it scores against folded strings. We keep one flat list and mix languages by convention in the seed data.

### 2. Scoring: reuse the existing tiered algorithm against canonical + each synonym

The existing `score-bls-match.ts` ranks five tiers (exact / whole-word / prefix / token-start / substring) for two strings (DE name and EN name). For FOODS, we apply the same algorithm to the canonical folded name and to *each* folded synonym, take the maximum, and use that as the entry's score.

To preserve the existing intuition that "the canonical name beats a synonym at the same tier", canonical matches use the German tier values (`{ exact: 100, wholeWord: 80, ... }`) and synonym matches use the (lower) English tier values (`{ exact: 90, wholeWord: 70, ... }`). This keeps "an exact synonym match outranks a substring canonical match" while ensuring "two entries that both whole-word-match: the one whose canonical name matched wins".

**Rejected:** flatten everything into one indexed list and score uniformly. We lose the canonical-vs-synonym tie-break, which matters when the seed list intentionally shares synonyms across entries (e.g. "Filet" appears as a synonym on multiple animal proteins).

### 3. Build script: deterministic, batched, AI tool-use

`backend/scripts/build-foods-data.ts` reads a curated TypeScript input file `scripts/foods-seed-keys.ts` shaped as:

```ts
export const FOODS_SEED_KEYS: ReadonlyArray<string> = [
  'moehre', 'tomate', 'zwiebel', /* ... ~100 ids in stable order ... */
];
```

The script calls Claude in batches (~20 keys per call) through the Anthropic SDK with a tool-use schema that mirrors `FoodEntry`. The model fills in the canonical name, synonyms, macros, unit, and pieces. Output entries are then sorted by `id`, validated, and written to `backend/data/foods.json`.

**Why a curated key list instead of free-form generation:** keeping the *what to include* decision in human hands (the seed-keys file) is the lever that prevents the AI from drifting in scope. The AI's job is filling in fields, not deciding which foods we cook with.

**Why batches of ~20:** small enough that one batch fits in a single tool call without truncation risk, large enough that ~150 entries is ~8 calls and the wall-clock cost is bearable. The tool-use schema also gives us a hard upper bound on shape per batch.

**Reproducibility:** macros for the same food vary slightly between sources (USDA vs BLS vs herstellerspezifisch). The script does not insist on bit-for-bit reproducibility — instead it commits the generated `foods.json` and treats the file as the source of truth. Re-running the script overwrites the file, but only the diff is reviewed in PR; small macro drift across reruns is acceptable.

**Rejected:** generating the keys themselves with AI ("give me the 150 staples"). That gives the AI two degrees of freedom (what to include, and what each entry contains), which is exactly what we want to avoid.

**Rejected:** per-entry retry-until-stable to force determinism. Adds complexity without solving the underlying "macros aren't a single canonical truth" problem.

### 4. Source-toggle UX flip

Before: `default sources = ['BLS']`. The drawer's toggle was labelled "Open Food Facts" and defaulted to off; localStorage key `forkcast:off-enabled` opted the user *into* OFF.

After: `default sources = ['OFF']` (in both the HTTP handler and the composite service). The drawer's toggle is labelled "FOODS" and defaults to off; localStorage key `forkcast:foods-enabled` opts the user *into* FOODS.

Rationale: the manual drawer is overwhelmingly used for branded products (yogurt, protein bars, supermarket items) where OFF wins. The curated FOODS source matters most to the AI recipe importer, which always queries FOODS explicitly. Keeping FOODS as opt-in in the drawer matches actual usage and prevents the small curated catalog from cluttering search-by-brand.

**Rejected:** keep the existing semantics and just rename `BLS → FOODS`. Would force users to always toggle if they wanted the OFF-first experience the user explicitly asked for.

**Rejected:** persist a single key like `forkcast:source-set` storing the array. Heavier than needed for a one-toggle UI.

### 5. Importer pins source explicitly

`importRecipeFromPhotos` currently calls `search.searchByName(raw.name)` with no `sources` argument, relying on the composite default. After this change the composite default flips to OFF — which would be a silent regression for the importer. We update the call site to `search.searchByName(raw.name, new Set(['FOODS']))` so the importer matches against the curated catalog regardless of HTTP defaults.

The `ai-recipe-import` spec is *not* modified: the spec language is "match it against the existing ingredient catalog" — that's still true; we're just being explicit at the call site. No spec scenarios change.

**Rejected:** wire two `IngredientSearchService` instances (one default-FOODS, one default-OFF) into the bootstrap and inject the right one into each consumer. Doubles the bootstrap surface for what is essentially a one-line argument at one call site.

### 6. File layout

```
backend/

  scripts/
    build-foods-data.ts                           # AI-driven build script
    foods-seed-keys.ts                            # curated key list (hand-edited)
  src/
    domain/
      foods/
        types.ts                                  # FoodEntry, FoodIndexedEntry, PieceWeight
        index-food-entry.ts                       # canonical+synonyms folding
        map-food-entry.ts                         # FoodEntry → IngredientSearchResult
      ingredient-search/

    infrastructure/
      ingredient-search/

```

Removed: `backend/BLS_4_0_Daten_2025_DE.csv`, `backend/data/bls.json`, `backend/scripts/build-bls-data.ts`, `backend/src/domain/bls/`, `backend/src/domain/ingredient-search/score-bls-match.ts`, `backend/src/infrastructure/ingredient-search/in-memory-bls.service.ts` (and their tests).

## Risks / Trade-offs

- **AI-generated macros may be wrong.** → Mitigation: each entry is reviewable in the JSON diff; the script is deterministic enough that re-running on the same key set produces a small, readable diff. We treat the JSON, not the script, as source of truth — hand corrections are stable across reruns only if we add the corrected macros back into the prompt as ground truth, but for v1 we accept that re-running may regress hand edits and document that workflow in the script header. Acceptable for a personal app where the user reviews every diff.
- **Synonym quality varies.** → Mitigation: canonical-name-only matches always score higher than synonym matches at the same tier, so a noisy synonym list mostly hurts recall, not precision. The seed keys file is the lever: missing entries are easy to add; bad synonyms can be removed by hand without re-running the AI.
- **Default flip surprises an existing user.** → Single-user app. The user is the same person reading this proposal. Acceptable.
- **Piece-weight data is unused in v1.** → We store it now because the AI seeding has marginal extra cost ("also include typical piece weights"), and it unlocks later UX (showing `1 mittlere Tomate ≈ 120 g` in the manual log) without re-running the AI. Trade-off: ~20% bigger JSON for fields we don't read yet. Acceptable.
- **Build script needs ANTHROPIC_API_KEY.** → Mitigation: same env var the recipe importer already uses; documented in the script header. The committed artifact means contributors who lack the key can still run the app.
- **Removing BLS deletes fallback for foods we forgot to seed.** → Mitigation: the OFF source covers the gap for branded products; for raw foods, we'd just add the missing key to `foods-seed-keys.ts` and re-run. We accept short-term recall regression in exchange for the dataset quality jump.

## Migration Plan

This is a single-user PR landing on `main` with no other consumers. No staged rollout.

1. Land the new code, the seed-keys file, and a hand-checked `foods.json` in one PR. The PR diff is the review.
2. Delete BLS files in the same PR.
3. After merge: redeploy the backend container; the bundled `foods.json` ships with the image. No data migration step — there is no DB.

**Rollback:** revert the PR. The deleted files and `bls.json` come back from git history.

## Open Questions

- Should we expose a small `/foods/by-id/:id` endpoint for future UX (e.g. tapping a piece-weight chip to recompute amounts)? Out of scope for v1; the JSON is in-memory anyway, and we can add the endpoint when we wire the UI that needs it.
- Should the AI build script also propose synonyms based on existing recipe ingredient names already logged in `recipes.json`? Possibly valuable later — for now, the AI's general-knowledge synonyms plus hand-curation cover v1.
