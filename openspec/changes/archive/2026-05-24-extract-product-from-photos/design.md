## Context

Barcode lookup today runs through `CompositeIngredientSearchService.searchByBarcode`, which delegates straight to `OpenFoodFactsService` (`InMemoryFoodsService` returns `null` — FOODS has no barcodes). On a miss the HTTP handler returns `404` and `search-panel.tsx` lands in the `barcode-not-found` state with only a "Try again" button — a dead end. Many local/store-brand German products (the REWE frozen-berry box that prompted this) aren't in OFF, yet the barcode is already known and the name + nutrition table are printed on the packaging.

The codebase already has every primitive this feature needs:
- **Vision extraction**: `AnthropicRecipeDraftExtractor` sends base64 images to `claude-sonnet-4-6` via a forced `tool_use` call and validates the result with a hand-written `parseToolInput`. It is gated behind `ANTHROPIC_API_KEY` in `index.ts` (503 `ai-import-not-configured` when unset) and bounded by `config.ai.recipeImport` image limits.
- **Image transport**: the frontend stages files (`photo-staging.tsx`), converts to base64 (`file-to-base64.ts`), and POSTs `{ images: [{ data, mediaType }] }`; the handler decodes + validates them.
- **Runtime-writable JSON stores**: recipes, weight-log, meal-log, unmatched-ingredients all `writeFile(..., JSON.stringify(x, null, 2))` atomically and are registered in `bootstrap([...])`.
- **Macro-snapshot logging**: `FullIngredientEntry` stores `macrosPerUnit` + `amount`, so a product only needs to reach `onSelect` as an `IngredientSearchResult` to be logged — no catalog membership required.

This change composes those primitives; it introduces no new dependency.

## Goals / Non-Goals

**Goals:**
- Turn the barcode not-found dead-end into a packaging-photo capture → AI extract → review/edit → log flow.
- Persist captured products keyed by barcode in a local store so re-scanning resolves instantly (no AI, no OFF round-trip).
- Keep the new AI path consistent with the recipe-import path (forced tool call, key-gating, image limits, error mapping, observability) by sharing the image-validation logic.
- Touch the existing barcode/search code only additively.

**Non-Goals:**
- Writing captured products into the curated `foods.json` catalog or the `build:foods` pipeline (that stays build-script-owned). Captured products live only in the new store.
- Editing or deleting stored scanned products after capture (re-capture overwrites; explicit management UI is out of scope).
- Reading the barcode from the photo — the scanned barcode is authoritative and passed through.
- Piece weights / synonyms / `untracked` on captured products (a scanned packaged product is mass/volume-tracked).

## Decisions

### 1. Separate `scanned-products.json` store, not an extension of `foods.json`
`FoodEntry` has no `barcode` field, and `foods.json` is regenerated by `build-foods-data.ts` (hand edits are overwritten). Adding runtime writes there would fight the build pipeline. Instead add a runtime-writable `backend/data/scanned-products.json` with its own entity:

```
ScannedProduct { barcode: string; name: string; unit: 'g' | 'ml'; macrosPer100: Macros; capturedAt: string }
```

A new `JsonScannedProductStore` mirrors the existing JSON-store adapters: `load()` on bootstrap, atomic `writeFile` on upsert, validation on read. It implements a domain port `ScannedProductStore { findByBarcode(barcode): Promise<ScannedProduct | null>; upsert(p): Promise<void> }`.

*Alternative considered:* add `barcode?` to `FoodEntry` and runtime-append to `foods.json`. Rejected — conflicts with the regeneration pipeline and the "save to local store, not curation" decision the user confirmed.

### 2. Barcode resolution order: local store → OFF
Thread the store into `CompositeIngredientSearchService` as a third (optional) constructor dependency. `searchByBarcode` checks the local store first; on a hit it maps to `IngredientSearchResult` (`source: 'SCAN'`) and returns without touching OFF; on a miss it falls back to `this.off.searchByBarcode` exactly as today.

Local-first is correct here: a product is only ever in the store *because* OFF missed (or the user corrected it), so the user's captured data should win and we save an OFF round-trip. `searchByName` is unchanged — the store is barcode-only.

*Alternative considered:* a separate outer service wrapping the composite. Rejected — `index.ts` already wires one `ingredientSearchService` for both endpoints; an extra constructor arg is the smaller, clearer change.

### 3. `'SCAN'` added to the result `source` union only — not to `IngredientSource`
`IngredientSearchResult.source` becomes `'FOODS' | 'OFF' | 'SCAN'`. The `IngredientSource` search-param type (used by the `sources` query param and the by-name fan-out) stays `'FOODS' | 'OFF'` — the scanned store is not a by-name search source. The frontend source badge already renders `result.source` generically, so it picks up the new label for free.

### 4. Two endpoints: read (`extract`) then write (`save`) — not one auto-saving call
`POST /extract-product-from-photos` is a pure read: it returns `{ barcode, name, unit, macrosPer100 }` and persists nothing. The user reviews/edits, then `POST /save-scanned-product` persists the edited values and returns the `SCAN` `IngredientSearchResult` for `onSelect`. Splitting keeps unreviewed/wrong AI output out of the store (matches the recipe-import "draft → review → add-recipe" shape) and keeps each endpoint single-purpose per CQRS.

*Alternative considered:* extract auto-saves, review issues a PATCH. Rejected — stores unverified data and needs an update/delete path we explicitly excluded.

### 5. New AI adapter `AnthropicProductDraftExtractor` with its own forced tool
A new `extract_product` tool with a tight schema (`name`, `unit`, `calories`, `protein`, `carbs`, `fat`) and a system prompt that says: read the name from the front, transcribe the **per-100** column verbatim, pick `unit` from "pro 100 g" vs "pro 100 ml", never invent values. A new `parseProductToolInput` validates (non-empty name; unit ∈ {g,ml}; calories finite ≥ 0; protein/carbs/fat finite ≥ 0, default 0). It reuses the existing `AnthropicLikeClient` interface so unit tests inject a fake client. The domain port is `ProductDraftExtractor { extract(images): Promise<ExtractedProduct> }`; the use case attaches the pass-through `barcode`.

*Alternative considered:* reuse `AnthropicRecipeDraftExtractor`. Rejected — the recipe tool/prompt model a different shape (ingredients/steps/pieces); a focused product tool extracts more reliably and validates more simply.

### 6. Share image decode/validation between both AI endpoints
Extract the image-list decode+limit logic currently inline in `import-recipe-from-photos.handler.ts` into a small pure helper (e.g. `http/ai-images/decode-image-payloads.ts`) returning either decoded `images` or a typed error (`{ status, body }`). Both handlers call it, so the limit semantics and error shapes (`imageIndex`, `413`, media-type message) stay identical. The recipe handler's existing tests pin the behavior and keep the refactor honest. Limits are reused from `config.ai.recipeImport` — no new env vars.

### 7. Frontend: new `extract-product-from-photos` feature, reusing staging primitives
Reuse `photo-staging.tsx` / `file-to-base64.ts` patterns rather than fork them. Extend the `barcode-not-found` branch of `search-panel.tsx` with a state machine: `not-found → capturing (stage photos) → extracting → review (edit form) → saving → onSelect`. New API client (`extract-product-from-photos.ts`, `save-scanned-product.ts`), a mutation hook, and German i18n strings. A `503 ai-import-not-configured` from extract hides/disables the capture entry point.

## Risks / Trade-offs

- **AI misreads the nutrition table (decimal commas, kJ vs kcal, per-portion vs per-100).** → The mandatory review/edit step is the guard; the prompt explicitly targets the per-100 column and kcal, and the user confirms before saving.
- **Refactoring the recipe handler's image validation could regress recipe import.** → The shared helper is a pure function with its own tests, and the recipe handler's existing endpoint tests must stay green; behavior/error shapes are preserved verbatim.
- **`scanned-products.json` grows unbounded / hand-edited / corrupt.** → Same risk profile and mitigation as the other JSON stores: validate on load, skip+warn on bad entries, atomic write. Volume is trivial (one row per personally-scanned product).
- **A wrong capture sticks because there's no edit/delete UI.** → Re-scanning the same barcode and re-capturing overwrites (upsert by barcode); explicit management is a deliberate non-goal for now.
- **Duplicate concept drift between OFF results and SCAN results.** → Both map to the same `IngredientSearchResult` shape with `macrosPerUnit = per100/100`, so the log/recently-used paths treat them identically; only the badge differs.

## Migration Plan

Additive only — no data migration. New file `backend/data/scanned-products.json` is created on first save (store handles a missing file as empty, like the other JSON stores) and registered in `bootstrap([...])`. The `IngredientSearchResult.source` union widening is backward compatible (existing producers still emit `FOODS`/`OFF`). No rollback steps beyond reverting the change; an orphaned `scanned-products.json` is inert if the feature is removed.

## Open Questions

- Should the review form let the user override `unit` (g↔ml), or trust the extracted unit? (Leaning: allow override — it's one field and guards a mislabeled liquid/solid.)
- Capture photo cap: reuse the recipe default (8) or set a smaller product-specific max (front + back ≈ 2–3)? (Leaning: reuse config; no new env var.)
- Should `recently-used-ingredients` visually distinguish `SCAN`-sourced entries, or is the existing name/macros snapshot enough? (Leaning: no special treatment — out of this change's scope.)
